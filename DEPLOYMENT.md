# Emergi-Access — Deployment

Public prototype for the Government of Maharashtra Hackathon. **Synthetic data only. Not a certified clinical system.**

| | URL |
|---|---|
| **Web application** | **https://emergi-access.vercel.app** |
| Backend API (Render) | https://emergi-access-api.onrender.com |
| Health check | https://emergi-access.vercel.app/health (proxied) · https://emergi-access-api.onrender.com/health (direct) |

## 1. Architecture

```
Browser ──HTTPS──▶ Vercel (static React build + CDN)
                     │  /api/*  and /health are proxied (vercel.json rewrites)
                     ▼
                   Render web service — Node 22, Express 5, Prisma        [Singapore]
                     │  TLS (sslmode=require)
                     ▼
                   Neon PostgreSQL (serverless)                           [AWS ap-southeast-1]
```

**Why Vercel proxies the API.** Authentication uses `HttpOnly`, `SameSite=Strict` session cookies plus a double-submit CSRF token that the frontend reads from a cookie. If the browser called `onrender.com` directly from `vercel.app`, those cookies would be third-party: blocked by Safari, and unreadable for CSRF in every browser. The Vercel rewrite keeps everything on one HTTPS origin, so the existing security model works unchanged and the API needs no wildcard CORS. The browser never contacts Render directly, and no `localhost` URL is used in production.

| Layer | Provider / plan | Notes |
|---|---|---|
| Frontend | Vercel Hobby (free) | Vite build, `frontend/vercel.json`: rewrites, SPA fallback, security and cache headers |
| Backend | Render Free web service | `render.yaml` Blueprint, auto-deploys from `main` |
| Database | Neon Free | Direct (non-pooled) connection, `connection_limit=5` |
| Source | GitHub (public) | `SamruddhiDoke/emergi-access` |

No paid service is used.

## 3. Environment variables

### Render (backend), set by `render.yaml`

| Variable | Value | Secret? |
|---|---|---|
| `DATABASE_URL` | Neon direct connection string + `&connection_limit=5` (must include `sslmode=require`) | **Yes**, entered in the Render dashboard, never committed |
| `JWT_SECRET` | Generated by Render (`generateValue`) | **Yes** |
| `OTP_SECRET` | Generated by Render (`generateValue`) | **Yes** |
| `CORS_ORIGINS` | `https://emergi-access.vercel.app` | No |
| `NODE_ENV` | `production` | No |
| `NODE_VERSION` | `22` | No |
| `COOKIE_SECURE` | `true` | No |
| `TRUST_PROXY` | `2` | No |
| `CLIENT_IP_HEADER` | `x-vercel-forwarded-for` (the visitor IP Vercel sends; measured) | No |
| `DEMO_MODE` | `true`, so simulated OTP codes appear on screen | No; **must be `false` with real users** |
| `SESSION_TTL_HOURS` | `8` | No |
| `AUTH_DURATION_SECONDS` | `300` (administrators can change it in-app) | No |

`PORT` is injected by Render. The server binds to `0.0.0.0:$PORT`.

### Vercel (frontend)

None are required. `VITE_API_BASE_URL` is intentionally left **empty** (same-origin `/api` via the rewrite). Never put secrets in `VITE_*` variables, because Vite embeds them in browser code.

## 4. How it was deployed (reproducible)

### 4.1 Database: Neon
1. https://console.neon.tech → New project `emergi-access`, region **AWS Asia Pacific (Singapore)**.
2. Click **Connect**, turn connection pooling **off**, and copy the direct string. Append `&connection_limit=5`.
   *Why direct:* Prisma keeps its own small pool, and `prisma migrate deploy` needs a direct connection. A pooled (`-pooler`) URL would need `pgbouncer=true` plus a separate `directUrl`.

### 4.2 Backend: Render
1. https://dashboard.render.com → **New → Blueprint** → repository `SamruddhiDoke/emergi-access`.
2. Render reads `render.yaml`: service `emergi-access-api`, **Free** plan, Singapore, root directory `backend`.
3. Enter `DATABASE_URL` (Neon) and `CORS_ORIGINS` (`https://emergi-access.vercel.app`), then **Apply**.
4. The build runs `npm ci && npx prisma generate && npx prisma migrate deploy`. The start runs `node prisma/seed.js --if-empty && node src/server.js`.
   - `prisma migrate deploy` only applies pending migrations. It never resets, drops or runs `migrate dev`.
   - `seed.js --if-empty` seeds synthetic demo data **only when the database has no users**. Otherwise it does nothing.
5. Health check path: `/health`.

### 4.3 Frontend: Vercel
Deployed with the Vercel CLI from `frontend/`:
```bash
cd frontend
npx vercel deploy --prod --yes --name emergi-access
```
`frontend/vercel.json` configures framework `vite`, `npm ci`, `npm run build` and output `dist`, plus:
- `/api/*` and `/health` → `https://emergi-access-api.onrender.com` (reverse proxy; 120 s proxy timeout, which covers Render's cold start)
- every other path except `/assets/*` → `index.html`, so deep links and refreshes work
- headers: HSTS, `X-Frame-Options: DENY`, `nosniff`, `Permissions-Policy: camera=(self)` (for QR scanning), long-term caching for hashed assets, `no-cache` for HTML

> `vercel.json` is the single place where the public backend hostname lives, as deployment configuration. If the Render URL ever changes, update both rewrite destinations.

## 5. Updating and redeploying

| Change | How to deploy |
|---|---|
| Backend code | `git push origin main`: Render auto-deploys (about 3–5 min) and applies new migrations during the build |
| Database schema | Create the migration locally with `npx prisma migrate dev --name <change>` **against your local database**, commit `prisma/migrations`, push. Render runs `migrate deploy` |
| Frontend code | `cd frontend && npx vercel deploy --prod --yes`. Optionally connect the GitHub repo in the Vercel dashboard (Project → Settings → Git, root directory `frontend`) for push-to-deploy |
| Render env var | Render dashboard → service → Environment (saving triggers a redeploy), or edit `render.yaml` and run **Blueprint → Manual Sync** |
| Roll back | Render: Events → pick a previous deploy → **Rollback**. Vercel: Deployments → previous → **Promote to Production** |

**Resetting the demo data is destructive.** `node prisma/seed.js` without `--if-empty` truncates every table. Only run it deliberately, with the production `DATABASE_URL` in your local environment, when you intend to wipe and recreate the demo dataset.

**Optional keep-warm during judging.** `deploy/keep-warm.yml` pings `/health` every 14 minutes so the free instance doesn't sleep. To enable it, copy it to `.github/workflows/`, push with a token that has the `workflow` scope, and set the repository variable `KEEP_WARM_URL=https://emergi-access.vercel.app/health`. Remove the variable after the event. One always-on free instance uses about 744 of Render's 750 monthly free hours.

## 6. Verification results (run against the public URLs)

All checks below were executed against `https://emergi-access.vercel.app` on 30 Oct 2026.

**Infrastructure**
- `/health` returns `200 {"status":"ok","database":"up"}`, both direct on Render and through the Vercel proxy (about 0.3 s when warm).
- Session cookies arrive as `Secure; SameSite=Strict` on the Vercel domain.
- Every route (`/`, `/register`, `/pro/login`, `/patient`, unknown paths) serves the SPA. HSTS, `Permissions-Policy` and caching headers are present.

**Judge scenario in a browser** (Playwright, `e2e/demo-scenario.mjs`): passed with no console errors.
- Patient sign-in, dashboard and QR (payload is only the Emergency ID), QR PNG download.
- Paramedic sign-in with OTP, QR scanned from the downloaded image, identification with no medical data.
- Reason, justification, acknowledgement, OTP, then the paramedic view: contacts visible; full medication list, mild allergy and minor condition withheld. Countdown running.
- Admin audit event inspected, then revoked. The paramedic screen switched to **Authorization revoked** on its own, with data cleared.
- Doctor view: medications and history visible, contacts withheld.
- Unverified professional denied.

**Navigation** (`e2e/navigation.mjs`, Edge 156 and Chromium): all 15 checks passed. These cover Get Started, refresh and direct load of `/register`, register ↔ login links, the 404 page, wrong-password and unreachable-API error messages, and no console errors.

**API checks against production**: all passed.
- Invalid login (401), unauthenticated admin request (401), CSRF mismatch (403).
- Patient refused from the admin API, paramedic refused from the patient API.
- Invalid Emergency ID rejected, identification contains no medical data, unverified professional denied.
- Specialist sees cardiology records only.
- **Real expiry:** with a 60 s duration, the server returned `410 AUTHORIZATION_EXPIRED` after the time elapsed. Duration restored to 300 s afterwards.
- Revocation returns `403 AUTHORIZATION_REVOKED`, and both the revocation and the refused request appear in the audit log.
- Admin metrics come from the database. Patient access history is populated.
- Audit records and rate limits use the real visitor IP (verified: the tester's public IP was recorded, not Render's Cloudflare edge addresses).
- Data persisted across a backend redeploy.

**Automated suites**: 48 backend tests and 14 frontend tests pass.

## 7. Known limitations

| Area | Limitation |
|---|---|
| Render Free | Sleeps after 15 min idle; the first request then takes up to about 1 minute. 750 instance-hours per month. Ephemeral filesystem (not used). In-memory rate-limit counters reset on restart or redeploy |
| Neon Free | 0.5 GB storage, 100 compute-hours per month per project. Compute suspends when idle (the first query after that is slightly slower) and stops until next month if quotas are exhausted |
| Vercel Hobby | Non-commercial use. 120 s proxy timeout. Runtime logs kept for 1 hour |
| OTP | Simulated; codes are displayed on screen (`DEMO_MODE=true`) |
| Professional verification | Manual administrator action; not connected to any licensing registry |
| Shared demo data | Judges share the same accounts, so they will see each other's activity in histories and audit logs |
| Client IP header | `x-vercel-forwarded-for` is trusted for audit and rate limiting. A client calling Render directly could spoof it to evade per-IP limits; all other controls are unaffected |
| Compliance | Prototype only. Production use would need encryption at rest, managed secrets, real OTP delivery, a registry integration, penetration testing and DPDP Act / ABDM review |
